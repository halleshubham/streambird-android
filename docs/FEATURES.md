# 0.2.0 - 0.3.0-ads: what was added

Scope of the app (decided): log in, see the integrated channels, brand setup, start a stream. No guests, wallpaper, background removal, screen share or recording.

## Look and feel
* The real StreamBird bird (`web-app/public/logo.png`, trimmed, copied to `res/drawable-nodpi/logo_bird.png`) is the launcher icon (adaptive, 108 dp, bird in the safe zone on `#F5F3FF`, monochrome layer for themed icons, legacy `mipmap-*` PNGs), the Android 12+ splash icon (`Theme.StreamBird.Starting`, core-splashscreen), the header of the login / "Your studio is being set up!" / "One more step" screens and the top bar of Channels. The "test logo" overlay is the same bird.
* `ui/theme/Theme.kt` maps the website tokens (`web-app/src/index.css`: `--accent #7c3aed`, `--text`, `--text-h`, `--bg`, `--card-bg`, `--border`, `--error`, `--warning`, and the dark set) onto a Material 3 light/dark scheme that follows the system, with 6 dp / 10 dp shapes and the website's type scale.
* `ui/screens/SbComponents.kt`: `Button` / `OutlinedButton` / `TextButton` / `Card` with the website's 6 dp radius, ghost-outline secondary buttons and bordered panels (declared in the screens' package so existing screens pick them up), `PlatformBadge` (YouTube red, Facebook blue, Twitch purple), `StatusBadge`, `Segmented` (pill control for visibility, quality, picture priority, logo position, lower-third style), `BirdTopBar`, `SubTopBar`, `PageHeading`. The Go live button carries the broadcast icon.

## 1. Brand kits (paid plans)
Channels -> "Brand kits" (or Setup -> Manage brand kits).
* **Brand screen** (`BrandScreen`): kits with a logo preview (position and size drawn as on air, GIF animated via Coil's GIF decoder), "Default" badge, the channels using each kit, "Use" for the next stream (default: Automatic = web rule), Edit, New. File library: used / quota bar, files with size, dimensions, `usedBy`, delete (a `409 used by the brand kits ...` is shown verbatim), "Upload a logo from the gallery".
* **Editor** (`BrandKitEditorScreen`): name, logo (library picker or upload; PNG/JPG/WebP/GIF, <= 4 MB, <= 8192 px, checked on the phone by `brand/ImageHeader.kt` and again by the backend), left/right, size slider 16..600, lower-third style bar/accent/glass (stored only; the app draws none), "use as account default", channel assignment (`PUT /brand-kits/connections/:id`, unticked = default), delete. Editing sends `wallpaperAssetId` / `wallpaperDim` back unchanged.
* **Setup**: when "Brand kit logo" is chosen, a Brand kit section (Automatic or a specific kit). The compositor (unchanged) draws the logo of the chosen kit; the kit is fetched again at go-live so edits apply.
* **Free plan** (`assetStorageMb == 0`): the screen explains it and links to `<server>/billing`; no brand calls are made. **Storage not enabled** (`/assets` `enabled:false`): amber notice, uploads disabled.
* An **animated GIF** logo is animated in the preview only; the GL compositor uses its first frame (`BitmapFactory` decodes one frame). Animating it on air is out of scope.

## 2. Thumbnail at start
Setup -> "Thumbnail (optional)" (Android photo picker, no storage permission). After `POST /streams` succeeds the app decodes the picture off the main thread (subsampled, EXIF-rotated, transparency flattened to white), fits it into 1280x720 (landscape) / 720x1280 (vertical stream; the server's `orientation` decides), never narrower than 640 px (backend minimum), JPEG quality 90 -> 42 and then smaller sizes until under 2 MB (`brand/ThumbnailPlan.kt`), and `PUT /streams/:id/thumbnail`. This runs in parallel to the WHIP publish, so go-live is never delayed, and failures never affect the stream. The Live screen shows a dismissible notice: uploaded, or the `platformWarnings` (e.g. YouTube needs a verified channel), or the error text.

## 3. Share live link
Channels: each connection with a `liveLinkUrl` shows the link with Copy (clipboard) and Share (ACTION_SEND, "Watch me live: <link>"). Live: "Share live link" shares the links of the destinations being streamed to (`liveLinkUrl`, else the destination `watchUrl`).

## 4. Send-quality chip
Top of the Live screen: "Sending 720x1280 - 30 fps - 2.4 Mbps", green dot; amber with the reason when limited. Same rules as `sendQuality.ts` (bandwidth, cpu, short side < 75 % of the chosen size; size check skipped in the first 6 s; `other` alone is not flagged). Texts: "Your connection is limiting quality. Try a lower quality or a better connection." / "Your phone is struggling. Try a lower quality." / "The picture is being sent smaller than the Np you chose. Try a lower quality or a better connection." The detailed stats table is behind a collapsed **Details** section; **Share log** is unchanged.

## 5. News ticker (0.2.1)
Same ticker as the web studio, available on every plan. Setup -> "Ticker (optional)": text (max 200 characters, line breaks and repeated spaces collapse; the web has no limit) and size S / M / L, remembered between runs (`Settings`). While live: **Ticker** button -> dialog with text, size, **Apply** (updates the running picture, no restart) and **Clear** (hides it).
* Rendering (`FrameCompositor.drawTicker`): the bar and the text are textured quads composed on the GL thread. The text is a Bitmap texture built with Android `Canvas` (sans-serif, white) only when the text or size changes (`TickerSpec.version`); per frame there is no bitmap work, just two draws positioned from the wall clock (`SystemClock.elapsedRealtime`). Vanilla theme colours: bar `rgba(0,0,0,0.65)`, text `#fff`.
* Geometry = `drawNewsline` / `newsBarHeight` scaled by `shortSide / 720`, so 540p / 720p / 1080p, portrait and landscape keep the web's proportions: font 18 / 28 / 44 web px for S / M / L (web range 12..120, default 18), bar `max(36, 1.9 x font)`, scroll 80 px/s at a 1280 px wide frame (a fixed share of the frame width), the text starts at the right edge, leaves on the left and restarts after a blank frame width (closed form of the web's loop, so frame-rate independent). Entrance: the bar slides up from below the frame in 400 ms (ease-out cubic) only when the ticker goes from hidden to shown, like `setNewsText`. Text wider than 4096 px is squeezed horizontally to fit one texture.
* The CSV log header has `ticker` (off / on size len) and every edit adds a `ticker on ...` / `ticker off` event row.

## 6. Surviving network changes (0.2.1)
Field log (Xiaomi, 720p landscape): cellular -> none -> wifi; afterwards frames kept being encoded but `rtt_ms`, `nack_count` and `pli_count` froze, i.e. no RTCP feedback came back: the ICE pair on the old interface was dead and nothing recovered it.
* **Detect** (every detection is a CSV event row): `ConnectivityManager` default-network callback (`NetworkWatcher`: new network, transport change, lost), peer-connection / ICE state (`DISCONNECTED` waits a 4 s grace, `FAILED` / `CLOSED` act at once), and a **stall detector** on the stats (`StallDetector`): `bytesSent` advancing while RTT, NACK/PLI counters and the candidate-pair receive counters (`bytesReceived`, `responsesReceived`, `roundTripTimeMeasurements`) stay unchanged for 7 s. A network change waits 3 s and is dropped if feedback is flowing again by then (libwebrtc migrated by itself).
* **Recover** (`StreamEngine.republish`, state machine `ReconnectMachine`, runner `Reconnector`): a NEW PeerConnection on the SAME tracks (camera, compositor, encoder pipeline, VideoSource and AudioSource are not touched), fresh WHIP POST to the same stream WHIP URL, wait until CONNECTED, swap, then DELETE the old WHIP resource and close the old connection. Sender parameters (max bitrate, degradation preference, bandwidth hint) are re-applied. Failed attempts (5xx, timeout, ICE not connecting; the new connection and any accepted WHIP session are cleaned up) retry after 1, 2, 4, 8, 16, then 30 s; a new network change replaces the pending attempt and restarts the fast schedule; no network = wait for one; give up after 5 minutes (the server ends the stream after the same time). The foreground service, wake/Wi-Fi locks and the server-side stream stay; `/streams/:id/end` is never called by the reconnect logic. ICE restart by WHIP `PATCH` is NOT used (MediaMTX does not offer it); the PeerConnection configuration is identical to 0.2.0 (0.2.1 added `GATHER_CONTINUALLY` and a 10 s STUN keep-alive; they were removed in 0.2.2, see below).
* **UI**: amber "Reconnecting... (attempt n)" banner (viewers see the "technical difficulties" slate meanwhile), notification text "Reconnecting...", then "Back online." Events: `detected: ...`, `republish attempt n`, `republished ok after X s`.
* **Server protocol it follows** (read from `mediamtx.service.ts`, `glitch-recovery.service.ts` and the web's `resumeLive`/`goLive`): MediaMTX path = `source: publisher`; `GlitchRecoveryService` waits 10 s without a publisher, then pushes the slate to the RTMP destinations for up to 5 minutes and stops it within 2 s after the publisher is back; the web re-publishes by POSTing a new offer to the same `whipUrl`. The app does exactly that. Gaps under 10 s never show the slate.
* **Debug aid**: Live -> Details -> "Simulate network drop" closes the transport under the running stream so the path can be tried without toggling networks. Setup shows an amber hint on mobile data ("a steady 3 Mbps upload is needed for 720p ...").
* Limits: the first attempt after a drop can fail for a few seconds if the server still holds the dead session and refuses a second publisher (see BACKEND-NEEDS.md); a re-publish restarts the RTMP forwarders (`runOnReadyRestart`), so the platforms see a short reconnect, as with the web; a very poor uplink (the 280 kbps / 1 s RTT case) is still limited by the network: the app only keeps the amber chip and the cellular hint for that.

## 7. 0.2.2: native crash after 0.2.1, diagnosis and hardening
**Report**: 0.2.1-brand crashed natively when pressing Go live (Xiaomi Redmi amethyst_in, Android 15): SIGSEGV on a libwebrtc-internal thread (`__pthread_start`), all frames in `libjingle_peerconnection_so.so` (BuildId 95dd82a22fc11dbb).
**Symbolication**: the build id matches `stream-webrtc-android-1.3.10` arm64-v8a, but the library is stripped (only 222 JNI exports in `.dynsym`), so no function names resolve. Disassembling the crash pc (file offset 0x6b3ffc, `.text`) shows `ldr x0,[x8,#-8]` or `mov x0,xzr`, then `ldr x8,[x0]; ldrsw x9,[x8,#0x2c]; add x8,x8,x9`: a virtual call through a NULL object pointer (null dereference, SIGSEGV at address 0), reached from a thread entry (`blr` of a virtual `Run`-style method). That is a libwebrtc task running on an object that is gone or never set, not a Java-side exception.
**Most likely causes** (not provable without symbols): (1) the `RTCConfiguration` options added in 0.2.1 (`continualGatheringPolicy = GATHER_CONTINUALLY`, `stunCandidateKeepaliveIntervalMs`), the only change on the first-connection path inside libwebrtc (about 50 % confidence); (2) PeerConnection lifecycle races introduced by the 0.2.1 refactor: stats polling, `setParameters` and `close/dispose` of a connection from different threads (about 25 %); (3) ticker/GL or watcher changes (low: they run on Java/GL threads, not in this library, and the watchers only start after the connection; about 10 %); unknown (about 15 %).
**Changes**: PeerConnection configuration reverted to exactly 0.2.0's (no continual gathering, no keep-alive); ALL connection lifecycle calls (create, negotiate, setParameters, getStats, close, dispose) run on ONE thread (`sb-pc`) with a generation counter and a `closed` flag; getStats/setParameters are guarded and wrapped in try/catch (a stats failure is logged, never thrown); the old connection is closed only after the new one is CONNECTED and disposed only after in-flight getStats calls finished; network/stall supervision starts only after the first stats plus 8 s of LIVE, and the network watcher ignores the initial replay of the current network (first 2 s).
**Crash reporting** (`diag/`): a default uncaught-exception handler writes the Java stack to `filesDir`; at every start `ActivityManager.getHistoricalProcessExitReasons` (API 30+: CRASH_NATIVE / CRASH / ANR) plus the native trace stream (tombstone summary, up to 64 KB) are combined with the last 200 events of a persistent ring-buffer log (`diag-events.log`: go live, pc created, offer, WHIP POST/answer, connected, republish, stats errors, ticker, network events) into a report. Channels and Setup show "The app closed unexpectedly last time" with Share crash report (share sheet, text file) and Dismiss.

## 8. 0.2.3: Live layout, following the server, stale streams
* **Live layout**: the preview is outside the scrolling area, in its own box sized to FIT the stream's aspect (9:16 or 16:9, letterboxed, never cropped) inside the space between the header and the controls (`fitInside`). Controls (chip, status text, Ticker, Share live link, Details, picture priority, destinations, events) scroll in a separate area below (portrait) or beside (landscape) it; Share log + End stream / Done are pinned at the bottom. Only two small overlays sit on the picture, both in the TOP corners: a status pill (top-left) and the flip-camera button (top-right); nothing near the bottom edge where the ticker bar is. The renderer uses `SCALE_ASPECT_FIT` and its box has exactly the frame aspect, so the preview shows what the compositor sends (720x1280 portrait with logo at a top corner and the ticker bar at the bottom).
* **Published frame review** (code only, not verified on a device): `FrameCompositor` crops in post-rotation space using `frame.rotatedWidth/rotatedHeight`; the 0.1.x log header (`camera 0 capture 1280x720@30 -> output 720x1280`) means the sensor frame arrives with rotation 90, rotated size 720x1280, i.e. the crop factor is (1, 1) and nothing is cropped or stretched; the front camera is only un-mirrored (x scale -1). Logo and ticker are drawn after the camera in output pixel space, so they cannot be misaligned relative to the output frame; the misalignment in the screenshots was the Compose layout of the preview (0.2.2 gave the preview `heightIn(max=420)` + `aspectRatio` inside a scrolling column, and a SurfaceView is not clipped/offset like normal Compose content).
* **Following the server**: `GET /streams/:id/status` every 5 s (was 10 s). A status other than `live` (ended on the website, force-ended, failed) or a 404 stops the stream here: engine, camera, reconnect supervision and the foreground service stop; `/end` is NOT called; the summary says "This stream was ended elsewhere ..." (or "stopped by the server"), and destination rows show `ended`, not a stale `live`. After the app's own End the final status is fetched once so rows show the real state. The ended summary returns to the start after 8 s, on Done, or on Back; Done/Back clear the live state (`LiveUi()`) so the next Go live starts clean; if the Setup screen is not in the back stack (app reopened from the notification) it navigates to Channels instead of staying on the Live screen (this was the "stuck on Live/Ended" cause). Back while live moves the app to the background and keeps streaming. Engine stop is bounded to 10 s.
* **Stale streams**: on start/refresh the app calls `GET /streams?limit=20`; any stream still `live` that this phone is not publishing is offered on Channels and Setup as "A stream is still marked live (title, started time)" with End stream (`POST /streams/:id/end`) and Dismiss (it could be a stream running from the website on purpose). Backend suggestion in BACKEND-NEEDS.md section 8.

## 9. 0.2.4: review fixes (concurrency, robustness)
* **Stream controller**: phase changes are claimed atomically (`tryMove`), so exactly one of End / "ended on the server" / the start coroutine wins. End during STARTING cancels and joins the start job before touching the engine, ends the stream created so far (once), and can never be followed by LIVE. Reconnect supervision is stopped first in every teardown. Auto-return timers carry a generation. The controller talks to the engine, service and Android through seams (`EnginePort`, `StreamEnv`), so these rules are unit-tested with fakes.
* **Engine**: `EngineLifecycle` = idempotent, NonCancellable teardown (order: camera frames, connection close, dispose, tracks, sources, compositor, capturer, factory, audio module, EGL, executors; the old 10 s cancel that could leave the camera held is gone), shared lock with republish. Republish closes the old connection first (frees the hardware encoder, both shared one track), then negotiates the new one and requires its `bytesSent` to advance before swapping; retired connections are disposed after in-flight stats and in `stop()`. Camera watchdog: no composed frame for 5 s -> restart capture (3x) -> clear "camera stopped" end of the stream. Factory/audio/camera are created off the main thread.
* **Reconnect**: network changes are debounced (2 s) and never cancel an attempt that is talking to the server; after giving up, the next detection re-arms with a fresh budget.
* **Data**: `ApiClient.call` is cancellable (also while the body is read), turns HTML 200s / bad JSON into `ApiException(-1)`, tolerates fields the backend may omit; asset downloads capped at 10 MB; `http://` server addresses are rejected except local/dev; `Settings` loads once in the background (started from `Application.onCreate`) and writes through one ordered writer, logout waits for the write; the app scope has an exception handler.
* **Misc**: foreground service always calls `startForeground` first, is idempotent and stops itself when the stream is over; compositor GL init is retried and fails loudly; logo decode bounded in both dimensions and recycled; shared cache files older than a day are purged; the stale-stream card never flags the app's own stream.

## 11. Advertisements (0.3.0-ads)
Mirrors the web studio (web-app/src/studio/ads.ts, adLayer.ts; spec also in the backend repo's `.claude/docs/studio.md`).
* **Placements** (one ad each, picture or animated GIF): lower third (full width, bottom third, moves UP by the ticker bar's height while the ticker shows), left third (left 1/3, full height), full screen. The picture is fitted INSIDE its area (contain, transparent letterbox, scaled up or down; lower third bottom-centre, others centred). Works for portrait and landscape from the stream's output size.
* **Schedule per ad**: continuous, or "show X, then hide Y" (`everySec` = hidden time; hidden first; 300 ms fades; cycle = hidden + shown). Full screen cross-fades the other two away. Manual Show now / Hide per ad from the Live screen (Ads sheet; eased over 300 ms, never saved; "Follow schedule" returns). The clock starts at 0 on the real go-live (LIVE) and is not restarted by a quiet reconnect. Draw order: camera, logo, ticker, then lower third, left third, full screen, then the Free mark last. The pure rules are `ads/Ads.kt`, with the web's test vectors ported to `AdsTest`.
* **Where ads come from**: the brand kit (the Brand screen's kit editor has an "Ads" section with the three slots, the library picker or an upload of kind `ad` from the gallery, the schedule editor with the web's validation messages) and a per-stream override on the Setup screen (switch off, change the schedule, or use a picture from the phone for THIS stream only: kept in memory, never uploaded, 12 MB / 8192 px caps like the web). Kit ads apply automatically with the kit; with no kit they are cleared but phone pictures stay. Each ad loads independently: a failing one is named in a message and the others and the logo are unaffected. The kit editor sends `ads` only when the user changed them; on plans without custom ads (and until the plan limits loaded) it is read-only with a "Remove ads" button and a billing link.
* **Rendering** (`media/AdLayerGl.kt`): ads are textures uploaded once, drawn as alpha-blended quads by the compositor after the ticker; no per-frame bitmap work or allocation; with no ads configured the frame is unchanged. GIFs: decoded lazily just before the ad can be seen, on a helper thread, with `ImageDecoder` + `AnimatedImageDrawable` (API 28+); frames are rendered into one reusable bitmap at most 15 times a second while the ad is visible and uploaded with `texSubImage2D`. Caps like the web: 150 frames and 96 MB in total (`planGif`, frame count read from the GIF blocks). On API 26/27, over the caps or on any decode failure the first frame is shown as a still and the host gets a note. Released at the end of the stream.
* **Log**: CSV header `ads`; event rows `ad <placement> on/off (schedule)` at go-live, `ad <placement> shown/hidden` once per transition (not per frame), manual changes, failures.
* **FREE PLAN (decision for the founder, flagged)**: the web's Free rule is applied to the app: on a plan with `watermark: true` custom ads are never drawn (nor decoded); instead the StreamBird banner (`streambird-ad-lower-third.png`, 1280x240, copied from the web) shows in the lower third 15 s every 180 s (hidden first), plus the small "Powered by StreamBird" mark (a port of poweredBy.ts: bottom-right, above the ticker, clear of the bottom edge on vertical streams) drawn last. The user cannot change or remove them (client-drawn: the same bypass caveat as the web). The founder had not decided this for Android yet; remove `freePlan` in `GoLiveRequest` (or the two draw calls in `AdLayerGl`) to switch it off.
* **Not verifiable without a device**: all rendering (textures, blending, positions, fades, the Powered-by pill), GIF decoding/animation and its frame-rate/CPU cost, `AnimatedImageDrawable.draw` outside a View (driven by its own clock without a callback), the layout of the new screens, and picking/reading pictures from the gallery.

## 10. Known remaining risks (not done)
* **R8/ProGuard**: release builds have `isMinifyEnabled = false`. Before enabling minification add keep rules for `org.webrtc.**` (JNI looks classes/methods up by name) and the Hilt/serialization entry points, and test a release build on a device.
* **Target SDK**: 35 now; Google Play requires the current target (36 from August 2026): re-test the foreground-service types, edge-to-edge and photo picker behaviour after the bump.
* **Release signing**: only debug-signed APKs exist; a release keystore, Play App Signing and an update channel are needed. Debug and release builds cannot update each other.
* **Foreground service declaration** (Play Console): `camera` and `microphone` types need a justification video and the in-app disclosure; Android 14+ needs the permissions granted before the service starts (the app asks first).
* **Data-safety items to declare**: email address (account), camera and microphone (live video/audio, sent to StreamBird servers and the destinations), optional photos (logo/thumbnail from the picker), crash/diagnostic reports the user chooses to share (device model, Android version, last 200 app events), and that the app falls back to Google's public STUN server (`stun.l.google.com:19302`) when the StreamBird TURN credentials cannot be fetched (the phone's IP is visible to it).
* **Not unit-testable here**: everything touching real camera, MediaCodec, WebRTC native code, GL, ConnectivityManager and the Compose layout; the controller and engine rules are tested with fakes, not on a device.

## Not verified on a device
Everything above is compiled and unit-tested (parsing, payloads, multipart bodies, sizing/compression decisions, share text, chip mapping, theme tokens) but **not run on a phone or emulator**: all new UI and its layout/colours in light and dark, the adaptive icon and splash rendering (including the themed monochrome icon), Coil image loading with the session cookie, GIF animation, the photo picker, real image decoding/EXIF rotation, uploads against the real backend (R2 storage, `platformWarnings` from YouTube/Facebook), the share sheet and clipboard. Added in 0.2.1 and also unverified on a phone: the ticker rendering (text quality, position, scroll smoothness, entrance, cost on the encoder), a REAL network switch (wifi <-> cellular <-> none), the actual WHIP re-publish against the production MediaMTX (override of a lingering publisher, slate hand-over to the platforms), `ConnectivityManager` callback behaviour on Android 15, and the simulate-drop button. Only the decision logic (state machine, backoff, stall detection incl. a replay of the frozen-feedback log, ticker maths) and the HTTP sequence (MockWebServer) are unit-tested.

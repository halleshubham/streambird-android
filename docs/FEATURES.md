# 0.2.0 - 1.0.0: what was added

Scope of the app (decided): log in, see the integrated channels, brand setup, start a stream. No guests, wallpaper drawing, background removal, screen share or recording.

## Look and feel
* The real StreamBird bird (`web-app/public/logo.png`, trimmed, copied to `res/drawable-nodpi/logo_bird.png`) is the launcher icon (adaptive, 108 dp, bird in the safe zone on `#F5F3FF`, monochrome layer for themed icons, legacy `mipmap-*` PNGs), the Android 12+ splash icon (`Theme.StreamBird.Starting`, core-splashscreen), the header of the login / "Your studio is being set up!" / "One more step" screens and the top bar of Channels. The "test logo" overlay is the same bird.
* `ui/theme/Theme.kt` maps the website tokens (`web-app/src/index.css`: `--accent #7c3aed`, `--text`, `--text-h`, `--bg`, `--card-bg`, `--border`, `--error`, `--warning`, and the dark set) onto a Material 3 light/dark scheme that follows the system, with 6 dp / 10 dp shapes and the website's type scale.
* `ui/screens/SbComponents.kt`: `Button` / `OutlinedButton` / `TextButton` / `Card` with the website's 6 dp radius, ghost-outline secondary buttons and bordered panels (declared in the screens' package so existing screens pick them up), `PlatformBadge` (YouTube red, Facebook blue, Twitch purple), `StatusBadge`, `Segmented` (pill control for visibility, quality, picture priority, logo position, lower-third style), `BirdTopBar`, `SubTopBar`, `PageHeading`. The Go live button carries the broadcast icon.

## 1. Brand kits (when the account's plan includes them)
Channels -> "Brand kits" (or Setup -> Manage brand kits).
* **Brand screen** (`BrandScreen`): kits with a logo preview (position and size drawn as on air, GIF animated via Coil's GIF decoder), "Default" badge, the channels using each kit, "Use" for the next stream (default: Automatic = web rule), Edit, a bin icon button (Delete, error colour, 48 dp; confirmation `Delete "<name>"?` with texts from `brand/KitDeleteText`, shared with the editor; message `Deleted "<name>".`), New. File library: used / quota bar, files with size, dimensions, `usedBy`, delete (a `409 used by the brand kits ...` is shown verbatim), "Upload a logo from the gallery".
* **Editor** (`BrandKitEditorScreen`): name, logo (library picker or upload; PNG/JPG/WebP/GIF, <= 8 MB (the server raised the per-file cap from 4 MB; the kit thumbnail stays 2 MB), <= 8192 px, checked on the phone by `brand/ImageHeader.kt` and again by the backend), left/right, size slider 16..600, lower-third style bar/accent/glass (stored only; the app draws none), "use as account default", channel assignment (`PUT /brand-kits/connections/:id`, unticked = default), delete. Editing sends `wallpaperAssetId` / `wallpaperDim` back unchanged.
* **Setup**: when "Brand kit logo" is chosen, a Brand kit section (Automatic or a specific kit). The compositor (unchanged) draws the logo of the chosen kit; the kit is fetched again at go-live so edits apply.
* **Plan without a brand library** (`assetStorageMb == 0`): the screen says plainly "Brand kits are not included in this account's plan" (no link, button, price or call to action; see "Play compliance" below); no brand calls are made. **Storage not enabled** (`/assets` `enabled:false`): amber notice, uploads disabled.
* An **animated GIF** logo is animated in the preview AND, since 1.0.8, on the broadcast (section 21): the compositor plays it from the wall clock; a long GIF plays an evenly spaced subset; the editor says when a GIF cannot animate on the stream.

## 2. Thumbnail at start
Setup -> "Thumbnail (optional)" (Android photo picker, no storage permission). After `POST /streams` succeeds the app decodes the picture off the main thread (subsampled, EXIF-rotated, transparency flattened to white), fits it into 1280x720 (landscape) / 720x1280 (vertical stream; the server's `orientation` decides), never narrower than 640 px (backend minimum), JPEG quality 90 -> 42 and then smaller sizes until under 2 MB (`brand/ThumbnailPlan.kt`), and `PUT /streams/:id/thumbnail`. This runs in parallel to the WHIP publish, so go-live is never delayed, and failures never affect the stream. The Live screen shows a dismissible notice: uploaded, or the `platformWarnings` (e.g. YouTube needs a verified channel), or the error text.

## 3. Share live link
Channels: each connection with a `liveLinkUrl` shows the link with Copy (clipboard) and Share (ACTION_SEND, "Watch me live: <link>"). Live: "Share live link" shares the links of the destinations being streamed to (`liveLinkUrl`, else the destination `watchUrl`).

## 4. Send-quality chip
Top of the Live screen: "Sending 720x1280 - 30 fps - 2.4 Mbps", green dot; amber with the reason when limited. Same rules as `sendQuality.ts` (bandwidth, cpu, short side < 75 % of the chosen size; size check skipped in the first 6 s; `other` alone is not flagged). Texts: "Your connection is limiting quality. Try a lower quality or a better connection." / "Your phone is struggling. Try a lower quality." / "The picture is being sent smaller than the Np you chose. Try a lower quality or a better connection." The detailed stats table is behind a collapsed **Details** section; **Share log** is unchanged.

## 5. News ticker (0.2.1)
Same ticker as the web studio, available on every plan. Setup -> "Ticker (optional)": text (max 200 characters, line breaks and repeated spaces collapse; the web has no limit) and size S / M / L, remembered between runs (`Settings`). While live: **Ticker** button -> dialog with text, size, **Apply** (updates the running picture, no restart) and **Clear** (hides it).
* Rendering (`FrameCompositor.drawTicker`): the bar and the text are textured quads composed on the GL thread. The text is a Bitmap texture built with Android `Canvas` (sans-serif, white) only when the text or size changes (`TickerSpec.version`); per frame there is no bitmap work, just two draws positioned from the wall clock (`SystemClock.elapsedRealtime`). Vanilla theme colours: bar `rgba(0,0,0,0.65)`, text `#fff`.
* Geometry = `drawNewsline` / `newsBarHeight` scaled by `shortSide / 720`, so 540p / 720p / 1080p, portrait and landscape keep the web's proportions: font 18 / 28 / 44 web px for S / M / L (web range 12..120, default 18), bar `max(36, 1.9 x font)`, scroll 80 px/s at a 1280 px wide frame (a fixed share of the frame width), the text starts at the right edge, leaves on the left and restarts after a blank frame width (closed form of the web's loop, so frame-rate independent). Entrance: the bar slides up from below the frame in 400 ms (ease-out cubic) only when the ticker goes from hidden to shown, like `setNewsText`. Text wider than 4096 px is squeezed horizontally to fit one texture.
* The CSV log header has `ticker` (off / on size len) and every edit adds a `ticker on ...` / `ticker off` event row.

## 6. Surviving network changes (0.2.1)
Field log (Xiaomi, 720p landscape): cellular -> none -> wifi; afterwards frames kept being encoded but `rtt_ms`, `nack_count` and `pli_count` froze, i.e. no RTCP feedback came back: the ICE pair on the old interface was dead and nothing recovered it.
* **Detect** (every detection is a CSV event row): `ConnectivityManager` default-network callback (`NetworkWatcher`: new network, transport change, lost), peer-connection / ICE state (`DISCONNECTED` waits a 4 s grace, `FAILED` / `CLOSED` act at once), and a **stall detector** on the stats (`StallDetector`): `bytesSent` advancing while RTT, NACK/PLI counters and the candidate-pair receive counters (`bytesReceived`, `responsesReceived`, `roundTripTimeMeasurements`) stay unchanged for 7 s. A network change waits 3 s and is dropped if feedback is flowing again by then (libwebrtc migrated by itself).
* **Recover** (`StreamEngine.republish`, state machine `ReconnectMachine`, runner `Reconnector`): a NEW PeerConnection on the SAME tracks (camera, compositor, encoder pipeline, VideoSource and AudioSource are not touched), fresh WHIP POST to the same stream WHIP URL, wait until CONNECTED, swap, then DELETE the old WHIP resource and close the old connection. Sender parameters (max bitrate, degradation preference, bandwidth hint) are re-applied. Failed attempts (5xx, timeout, ICE not connecting; the new connection and any accepted WHIP session are cleaned up) retry after 1, 2, 4, 8, 16, then 30 s; a new network change replaces the pending attempt and restarts the fast schedule; no network = wait for one; give up after 5 minutes (the server ends the stream after the same time). The foreground service, wake/Wi-Fi locks and the server-side stream stay; `/streams/:id/end` is never called by the reconnect logic. ICE restart by WHIP `PATCH` is NOT used (MediaMTX does not offer it); the PeerConnection configuration is identical to 0.2.0 (0.2.1 added `GATHER_CONTINUALLY` and a 10 s STUN keep-alive; they were removed in 0.2.2, see below).
* **UI**: amber "Reconnecting... (attempt n)" banner (viewers see the "technical difficulties" slate meanwhile), notification text "Reconnecting...", then "Back online." Events: `detected: ...`, `republish attempt n`, `republished ok after X s`.
* **Server protocol it follows** (read from `mediamtx.service.ts`, `glitch-recovery.service.ts` and the web's `resumeLive`/`goLive`): MediaMTX path = `source: publisher`; `GlitchRecoveryService` waits 10 s without a publisher, then pushes the slate to the RTMP destinations for up to 5 minutes and stops it within 2 s after the publisher is back; the web re-publishes by POSTing a new offer to the same `whipUrl`. The app does exactly that. Gaps under 10 s never show the slate.
* **Debug aid**: Live -> Details -> "Simulate network drop" closes the transport under the running stream so the path can be tried without toggling networks. Setup shows an amber hint on mobile data ("a steady 3 Mbps upload is needed for 720p ...").
* Limits: the first attempt after a drop can fail for a few seconds if the server still holds the dead session and refuses a second publisher (see BACKEND-NEEDS.md); a re-publish restarts the RTMP forwarders (`runOnReadyRestart`), so the platforms see a short reconnect, as with the web; a very poor uplink (the 280 kbps / 1 s RTT case) is still limited by the network: the app only keeps the amber chip and the cellular hint for that.

## 7. 0.2.2: native crash after 0.2.1, diagnosis and hardening
**Report**: 0.2.1-brand crashed natively when pressing Go live (Xiaomi Redmi amethyst_in, Android 15): SIGSEGV on a libwebrtc-internal thread (`__pthread_start`), all frames in `libjingle_peerconnection_so.so` (BuildId 95dd82a22fc11dbb).
**Symbolication**: the build id matches `stream-webrtc-android-1.3.10` arm64-v8a, but the library is stripped (only 222 JNI exports in `.dynsym`), so no function names resolve. Disassembling the crash pc (file offset 0x6b3ffc, `.text`) shows `ldr x0,[x8,#-8]` or `mov x0,xzr`, then `ldr x8,[x0]; ldrsw x9,[x8,#0x2c]; add x8,x8,x9`: a virtual call through a NULL object pointer (null dereference, SIGSEGV at address 0), reached from a thread entry (`blr` of a virtual `Run`-style method). That is a libwebrtc task running on an object that is gone or never set, not a Java-side exception.
**Most likely causes** (not provable without symbols): (1) the `RTCConfiguration` options added in 0.2.1 (`continualGatheringPolicy = GATHER_CONTINUALLY`, `stunCandidateKeepaliveIntervalMs`), the only change on the first-connection path inside libwebrtc (about 50 % confidence); (2) PeerConnection lifecycle races introduced by the 0.2.1 refactor: stats polling, `setParameters` and `close/dispose` of a connection from different threads (about 25 %); (3) ticker/GL or watcher changes (low: they run on Java/GL threads, not in this library, and the watchers only start after the connection; about 10 %); unknown (about 15 %).
**Changes**: PeerConnection configuration reverted to exactly 0.2.0's (no continual gathering, no keep-alive); ALL connection lifecycle calls (create, negotiate, setParameters, getStats, close, dispose) run on ONE thread (`sb-pc`) with a generation counter and a `closed` flag; getStats/setParameters are guarded and wrapped in try/catch (a stats failure is logged, never thrown); the old connection is closed only after the new one is CONNECTED and disposed only after in-flight getStats calls finished; network/stall supervision starts only after the first stats plus 8 s of LIVE, and the network watcher ignores the initial replay of the current network (first 2 s).
**Crash reporting** (`diag/`): a default uncaught-exception handler writes the Java stack to `filesDir`; at every start `ActivityManager.getHistoricalProcessExitReasons` (API 30+: CRASH_NATIVE / CRASH / ANR) plus the native trace stream (tombstone summary, up to 64 KB) are combined with the last 200 events of a persistent ring-buffer log (`diag-events.log`: go live, pc created, offer, WHIP POST/answer, connected, republish, stats errors, ticker, network events) into a report. Channels and Setup show "The app closed unexpectedly last time" with Share crash report (share sheet, text file) and Dismiss.

## 8. 0.2.3: Live layout, following the server, stale streams
* **Live layout**: the preview is outside the scrolling area, in its own box sized to FIT the stream's aspect (9:16 or 16:9, letterboxed, never cropped) inside the space between the header and the controls (`fitInside`). Controls (chip, status text, Ticker, Share live link, Details, picture priority, destinations, events) scroll in a separate area below (portrait) or beside (landscape) it; Share log + End stream / Done are pinned at the bottom. Only two small overlays sit on the picture, both in the TOP corners: a status pill (top-left) and the flip-camera button (top-right); nothing near the bottom edge where the ticker bar is. The renderer uses `SCALE_ASPECT_FIT` and its box has exactly the frame aspect, so the preview shows what the compositor sends (720x1280 portrait with logo at a top corner and the ticker bar at the bottom).
* **Published frame review** (code only, not verified on a device): `FrameCompositor` crops in post-rotation space using `frame.rotatedWidth/rotatedHeight`; the 0.1.x log header (`camera 0 capture 1280x720@30 -> output 720x1280`) means the sensor frame arrives with rotation 90, rotated size 720x1280, i.e. the crop factor is (1, 1) and nothing is cropped or stretched; the front camera is only un-mirrored (x scale -1). Logo and ticker are drawn after the camera in output pixel space, so they cannot be misaligned relative to the output frame; the misalignment in the screenshots was the Compose layout of the preview (0.2.2 gave the preview `heightIn(max=420)` + `aspectRatio` inside a scrolling column, and a SurfaceView is not clipped/offset like normal Compose content).
* **Following the server**: `GET /streams/:id/status` every 5 s (was 10 s). A status other than `live` (ended on the website, force-ended, failed) or a 404 stops the stream here: engine, camera, reconnect supervision and the foreground service stop; `/end` is NOT called; the summary says "This stream was ended elsewhere ..." (or "stopped by the server"), and destination rows show `ended`, not a stale `live`. After the app's own End the final status is fetched once so rows show the real state. The ended summary returns to the start after 8 s, on Done, or on Back; Done/Back clear the live state (`LiveUi()`) so the next Go live starts clean; if the Setup screen is not in the back stack (app reopened from the notification) it navigates to Channels instead of staying on the Live screen (this was the "stuck on Live/Ended" cause). Back while live moves the app to the background and keeps streaming. Engine stop is bounded to 10 s.
* **Stale streams**: on start/refresh the app calls `GET /streams?limit=20`; any stream still `live` that this phone is not publishing is offered on Channels and Setup as "A stream is still marked live (title, started time)" with End stream (`POST /streams/:id/end`) and Dismiss (it could be a stream running from the website on purpose). Backend suggestion in BACKEND-NEEDS.md section 8.

## 9. 0.2.4: review fixes (concurrency, robustness)
* **Stream controller**: phase changes are claimed atomically (`tryMove`), so exactly one of End / "ended on the server" / the start coroutine wins. End during STARTING cancels and joins the start job before touching the engine, ends the stream created so far (once), and can never be followed by LIVE. Reconnect supervision is stopped first in every teardown. Auto-return timers carry a generation. The controller talks to the engine, service and Android through seams (`EnginePort`, `StreamEnv`), so these rules are unit-tested with fakes.
* **Engine**: `EngineLifecycle` = idempotent, NonCancellable teardown (order: camera frames, connection close, dispose, tracks, sources, compositor, capturer, factory, audio module, EGL, executors; the old 10 s cancel that could leave the camera held is gone), shared lock with republish. Republish closes the old connection first (frees the hardware encoder, both shared one track), then negotiates the new one and requires its `bytesSent` to advance before swapping; retired connections are disposed after in-flight stats and in `stop()`. Camera watchdog: no composed frame for 5 s -> restart capture (3x) -> clear "camera stopped" end of the stream. Factory/audio/camera are created off the main thread.
* **Reconnect**: network changes are debounced (2 s) and never cancel an attempt that is talking to the server; after giving up, the next detection re-arms with a fresh budget.
* **Data**: `ApiClient.call` is cancellable (also while the body is read), turns HTML 200s / bad JSON into `ApiException(-1)`, tolerates fields the backend may omit; asset downloads capped at 10 MB; `http://` server addresses are rejected except local/dev; `Settings` loads once in the background (started from `Application.onCreate`) and writes through one ordered writer, logout waits for the write; the app scope has an exception handler.
* **Misc**: foreground service always calls `startForeground` first, is idempotent and stops itself when the stream is over; compositor GL init is retried and fails loudly; logo decode bounded in both dimensions and recycled; shared cache files older than a day are purged; the stale-stream card never flags the app's own stream.

## 11. Advertisements (0.3.0-ads)
Mirrors the web studio (web-app/src/studio/ads.ts, adLayer.ts; spec also in the backend repo's `.claude/docs/studio.md`).
* **Placements** (one ad each, picture or animated GIF): lower third (full width, bottom third, moves UP by the ticker bar's height while the ticker shows), left third (left 1/3, full height), full screen, and since 1.0.8 the L-shaped frame (full frame with a window, section 20). The picture is fitted INSIDE its area (contain, transparent letterbox, scaled up or down; lower third bottom-centre, others centred). Works for portrait and landscape from the stream's output size.
* **Schedule per ad**: continuous, or "show X, then hide Y" (`everySec` = hidden time; hidden first; 300 ms fades; cycle = hidden + shown). Full screen cross-fades the other two away. Manual Show now / Hide per ad from the Live screen (Ads sheet; eased over 300 ms, never saved; "Follow schedule" returns). The clock starts at 0 on the real go-live (LIVE) and is not restarted by a quiet reconnect. Draw order: camera, logo, ticker, then lower third, left third, full screen, then the Free mark last. The pure rules are `ads/Ads.kt`, with the web's test vectors ported to `AdsTest`.
* **Where ads come from**: the brand kit (the Brand screen's kit editor has an "Ads" section with the three slots, the library picker or an upload of kind `ad` from the gallery, the schedule editor with the web's validation messages) and a per-stream override on the Setup screen (switch off, change the schedule, or use a picture from the phone for THIS stream only: kept in memory, never uploaded, 12 MB / 8192 px caps like the web). Kit ads apply automatically with the kit; with no kit they are cleared but phone pictures stay. Each ad loads independently: a failing one is named in a message and the others and the logo are unaffected. The kit editor sends `ads` only when the user changed them; on plans without custom ads (and until the plan limits loaded) it is read-only with a "Remove ads" button and a billing link.
* **Rendering** (`media/AdLayerGl.kt`): ads are textures uploaded once, drawn as alpha-blended quads by the compositor after the ticker; no per-frame bitmap work or allocation; with no ads configured the frame is unchanged. GIFs: decoded lazily just before the ad can be seen, on a helper thread, with `ImageDecoder` + `AnimatedImageDrawable` (API 28+); frames are rendered into one reusable bitmap at most 15 times a second while the ad is visible and uploaded with `texSubImage2D`. Caps like the web: 150 frames and 96 MB in total (`planGif`, frame count read from the GIF blocks). On API 26/27, over the caps or on any decode failure the first frame is shown as a still and the host gets a note. Released at the end of the stream.
* **Log**: CSV header `ads`; event rows `ad <placement> on/off (schedule)` at go-live, `ad <placement> shown/hidden` once per transition (not per frame), manual changes, failures.
* **FREE PLAN (decision for the founder, flagged)**: the web's Free rule is applied to the app: on a plan with `watermark: true` custom ads are never drawn (nor decoded); instead the StreamBird banner (`streambird-ad-lower-third.png`, 1280x240, copied from the web) shows in the lower third 15 s every 180 s (hidden first), plus the small "Powered by StreamBird" mark (a port of poweredBy.ts: bottom-right, above the ticker, clear of the bottom edge on vertical streams) drawn last. The user cannot change or remove them (client-drawn: the same bypass caveat as the web). The founder had not decided this for Android yet; remove `freePlan` in `GoLiveRequest` (or the two draw calls in `AdLayerGl`) to switch it off.
* **Not verifiable without a device**: all rendering (textures, blending, positions, fades, the Powered-by pill), GIF decoding/animation and its frame-rate/CPU cost, `AnimatedImageDrawable.draw` outside a View (driven by its own clock without a callback), the layout of the new screens, and picking/reading pictures from the gallery.

## 12. Unified brand kit, 16:9 / 9:16 sets, picture shrink (0.4.0-orientation)
Mirrors the web (PR "brand-orientation": `brandSizes.ts`, `brandKitSet.ts`, `ads.ts` shrinkEase / adReserve / sceneRect / sceneRectFor, `adLayer.ts`, backend `brand-kits.service.ts`). The backend fields below only exist in production once that web PR is deployed; the app tolerates their absence (see "Older servers").
* **One editor, no upload-vs-create split** (`BrandKitEditorScreen`, `BrandSlots.kt`): a 16:9 | 9:16 toggle, then one card per slot: Logo, Wallpaper, Lower third, Left third, Full screen. Each card does everything in place: Upload (Replace when filled), "Choose from uploaded" (library filtered by kind: `logo`, `wallpaper`/`background`, `ad`), preview, Remove, the suggested size and file rules, and a non-blocking amber warning when the chosen picture's shape is off by more than 1.5x. Ad cards also carry the on/off switch and the schedule editor. Shared by both sets: logo position, logo size, lower-third style, the shrink switch, default, channels.
* **Numbers** (`brand/BrandSizes.kt`, same as `brandSizes.ts`): logo 512x512 (up to 1024; ratio 0.4..5); wallpaper 1920x1080 / 1080x1920; lower third 1280x240 / 1080x360; left third 640x1080 / 360x1920; full screen 1920x1080 / 1080x1920; 8 MB (4 MB before 1.0.9), 8192 px; GIF only for logo and ads (wallpaper upload refuses GIF on the phone). Warning ratio range = suggested ratio / 1.5 .. x 1.5. The warning uses the width/height the library reports for the chosen file.
* **Kit API fields**: landscape keeps `logoAssetId`, `wallpaperAssetId`, `ads`; portrait uses `logoAssetIdPortrait`, `wallpaperAssetIdPortrait`, `adsPortrait`; shared `logoPosition`, `logoSize`, `wallpaperDim`, `lowerThirdStyle`, `adsShrinkPicture` (default true). Ads are replace-all per set: omitted/null = unchanged, `[]` = none; the app sends a set's ads only when the user changed that set. Logos/wallpapers: an explicit null clears.
* **Which set a stream uses** (`kitSetFor`, same rule as `brandKitSet.ts`): landscape stream -> landscape set; portrait stream -> portrait set, and ONLY the logo falls back to the landscape logo (wallpaper and ads do not fall back). Applied to the logo load, the ads load and the Setup screen's ad list.
* **Older servers**: every new response field has a default (portrait ids null, `adsPortrait` empty, `adsShrinkPicture` true), so an old response parses and a portrait stream then simply has no portrait wallpaper/ads and the landscape logo. Requests to an older server never contain a new field unless the user changed it (`BrandKitPayload.patch`: unchanged portrait ids / shrink / `adsPortrait` are omitted), so editing a kit with an old server keeps working; saving a 9:16 change against an old server is refused by that server (400).
* **Picture shrinks while an ad shows** (`ads/AdShrink.kt` = line-by-line port of the web formulas, `AdLayerGl.update/sceneRect`, `FrameCompositor`): while a lower third or left third ad is visible the scene (camera and logo; the app has no name lower third) is scaled, aspect kept, into the rectangle the ad leaves free and centred there over the black background: lower third = above the DRAWN ad picture (already above the ticker), left third = the right two thirds, both = the intersection, full screen = no shrink. Progress = `shrinkEase` (smoothstep) of each ad's current opacity (the 300 ms fade), so the picture eases in step with the ad. The ticker stays on the bottom edge, the Free-plan "Powered by" mark is drawn last on top. The Free plan's StreamBird banner is a lower-third ad and shrinks the picture the same way (the web's `adLayer.sceneRect` does this too).
* **Switches**: per kit `adsShrinkPicture` (editor, default on); per stream override on Setup (Ads section) and live in the Live "Ads" sheet (not saved to the kit). Order: override, else the kit, else on. The frame is byte-for-byte what it was before when nothing shrinks it (no ads, switch off, or no lower/left third visible).
* **Wallpaper**: stored on the kit and editable, but still not drawn by the app (as before): the area around a shrunk picture is the compositor's black.
* **Tests** (JVM): `AdShrinkTest` (shrinkEase, adReserve, sceneRect, sceneRectFor incl. portrait, ticker, both ads, bounds), `BrandSizesTest` (sizes, limits, GIF rule, warning logic, kit-set selection, old/new response parsing), `BrandOrientationApiTest` (payloads: omit = unchanged, `[]` clears, nothing new sent to an old server), controller tests (orientation picks the set, shrink default / override / live switch).
* **Not verifiable without a device**: the GL scene placement (viewport maths, logo placement/scale inside the shrunk scene, ease timing against the fade), the new editor layout, uploads of wallpaper/portrait files from the gallery.

## 13. One-tap go-live and saved presets (0.5.0-presets)
Design direction "A (one-tap, camera first) + C (saved presets)": the app used to ask for channels, title, quality, logo, ads, ticker and thumbnail before anything happened. Now home is a list of ready-made cards and going live is one tap on a camera screen. Nothing was removed: the old controls moved behind "Customize".
* **Home** (`HomeScreen`, start screen): "Ready when you are". Cards come from `GET /api/presets`, most recently used first. The first card is the purple gradient one (name, one-line summary `YouTube + Facebook · Acme brand · Ticker on · 720p`, white "Go live now"); the others are lighter rows with a "Go live" button. A dashed "+ New preset" card is last. The "..." menu of a saved card: Edit (opens the camera screen with Customize already open) and Delete (confirmation). Under the cards: "Pick channels and set up by hand" (the previous Channels -> Setup flow, unchanged), Brand kits, connect on the website, Refresh. Stale-stream and crash-report cards stay at the top.
* **Camera-first screen** (`GoLiveScreen`, route `go`): the camera fills the screen (`media/PreviewCamera`: the same WebRTC Camera2 capturer the engine uses, drawn into a `SurfaceViewRenderer`, no encoder or network; it is stopped before the stream starts because the engine opens the camera itself). Top row: close, status pill ("Camera and mic ready", or "Allow camera and mic" - tap it or the black screen to ask), flip camera. Bottom gradient panel: big title ("Add a title..." until set; tap to edit in a dialog), destination chips (every connected channel: ticked = purple pill with the platform name, unticked = grey "+ Twitch"; same plan limit and note as before), a large red full-width "Go live", and the line "Acme brand · 720p · Ticker off" with "Customize" on the right.
* **Go live is one tap**: same permission flow as Setup (`rememberGoLive`: camera and microphone, notifications on Android 13+; the stream starts when they are granted). If a saved preset is open, `POST /api/presets/:id/use` is sent in the background (never blocks or fails the stream).
* **Customize** (bottom sheet): everything the Setup screen has, as the same composable (`SetupFields`: title, visibility, shape, quality, picture priority, logo overlay, brand kit, ads, ticker, thumbnail, front camera, experiments), plus a "Save as preset" / "Preset" block (name, Save or Update, Delete) when the server has presets. Manage brand kits leaves the sheet for the Brand screen.

## 17. Google sign-in in the browser (1.0.5, made the only Google sign-in in 1.0.6)
* **Flow** (`auth/BrowserSignIn.kt`, `AuthRepository.beginBrowserSignIn` / `handleAuthLink`): PKCE-style handoff, no Google client on the phone. The app makes a verifier (32 secure random bytes, 43 chars base64url) and challenge = base64url(SHA-256(verifier)), stores the verifier in SharedPreferences with a timestamp (valid 10 minutes; the process can be killed while the browser is in front), and opens `<server>/api/auth/google/app?challenge=...` in a Chrome Custom Tab (`androidx.browser:browser:1.8.0`; plain VIEW intent without a provider; "No browser found" note if neither works). The server sends the browser through Google and finally to `streambird://auth?code=<code>` (or `?error=google_failed`). `MainActivity` (`launchMode="singleTask"`) has a VIEW/DEFAULT/BROWSABLE filter for `streambird://auth`, handles the cold-start intent and `onNewIntent`, and strips the data after handling. A code is redeemed with `POST /api/auth/google/app/redeem {code, verifier}`; the answer goes through `applyUser` like every login (NEEDS_PHONE / PENDING / READY). While redeeming the button and a line read "Signing you in..." (`GoogleStage.REDEEMING`). The verifier is cleared after every redeem attempt, an error link, and when stale (10 minutes).
* **Diagnostics**: `google-browser: ...` lines in the event log (`diag/Diag`, last 200 events, part of every crash report): started, redeem ok / failed with the HTTP status, link without pending sign-in, link error, "returned without a code". The code and verifier are never logged. "Share sign-in diagnostics" (shares that log) appears under the Google button only after an attempt that ended without success (note shown or error).
* **Messages**: no pending sign-in -> "That sign-in link is not valid any more. Start again with "Continue with Google"."; older than 10 min -> "That sign-in took too long ..."; 400 / 401 -> "Google sign-in could not be completed. Try again or use the email code."; 404 (server without the endpoints) -> "Google sign-in is not available on this server yet. Use the email code."; 429 -> rate-limit text; network -> "Cannot reach the server: ..."; `error=google_failed`, an unusable link, an unexpected failure, or coming back without a code -> "Google sign-in did not finish. Try again, or use the email code." Links with another scheme/host or while already signed in are ignored.
* **Security**: the custom scheme is not a trust boundary. Anyone can fire `streambird://auth?code=x`, but a code is only worth something together with the verifier, which never leaves the app before the redeem (the URL carries only the challenge). A forged link can at worst consume the pending attempt (the person taps the button again).
* **Tests** (JVM): `auth/BrowserSignInTest` (verifier / challenge length, charset, RFC 7636 test vector, uniqueness, link parsing, expiry logic behind `PendingVerifierStore`, error mapping), `data/BrowserLoginTest` (button -> verifier/challenge -> start URL -> deep link code -> redeem -> NEEDS_PHONE / PENDING / READY, redeem body is only `code` + `verifier`, absent and stale verifier, error link, 400/401/404/429, network, verifier cleared after each attempt, Back from the browser, no-browser fallback).
* **Not verified (no device)**: the Custom Tab opening, the `streambird://` return into the running task, the cold start from the link, process death while the browser is in front, Back from the tab, the diagnostics share sheet.

Spec = the website's `ads.ts` / `adWindow.ts` and the "L-shaped (frame) ads" section of its `.claude/docs/studio.md`.

* **Geometry** (`ads/Ads.kt`, `ads/AdShrink.kt`): `adRect(L_SHAPE)` = the whole frame; the picture is contain-fitted and centred (`fitAd`); window on the frame = fitted origin + window x fitted size (`windowOnCanvas`); the scene goes into it with `lShapeSceneRect` (scale = min(1, win.w/W, win.h/H), aspect kept, centred in the window) and `sceneRectFor` eases from the rect the other ads leave to the window with `shrinkEase` (smoothstep) of the frame's opacity.

## 21. Animated GIF logo on the broadcast (1.0.8)
* **Before**: the preview animated a GIF logo but the broadcast used its first frame. **Now** the broadcast animates it, with the same safety caps as the animated ads (150 frames, 96 MB of decoded pixels) but WITHOUT giving up on long GIFs.
* **Why a new decoder**: `AnimatedImageDrawable` (used for ads) plays on its own clock and cannot drop frames. The logo uses `media/GifFrames.kt`: a small GIF parser/decoder (LZW, local/global palettes, transparency, interlace, disposal methods 0-3) that composes every frame but keeps only the chosen ones. Works on API 26+ (no `ImageDecoder`).
* **Plan** (`planGifLogo`): decode height = `min(GIF height, max(256, 2 x logo size))` (the web's rule); `allowed = min(150, 96 MB / (w x h x 4))`. All frames when they fit; otherwise `allowed` evenly spaced frames (source index `j x n / allowed`) and the delays of the skipped frames are MERGED into the kept ones, so the loop keeps its length. Only when fewer than two frames would fit it stays the first frame. Delays: 0/1 cs = 100 ms, otherwise >= 20 ms (web `frameDelayMs`).
* **Playing**: `StreamController` starts the broadcast with the first frame as before, decodes the frames in the background (`LogoAnimationLoader`, Default dispatcher; out-of-memory or damage = stays still) and hands them to the compositor (`LogoOverlay.animation`); `FrameCompositor.currentLogoTexture` picks the frame from the wall clock (`frameIndexAt`, loops) and uploads it with `texSubImage2D` only when the frame changes; any exception falls back to the still logo. Frames are recycled when the stream ends. The Live event log says "logo animated: N frames (of M)" or why it stays a still.
* **Editor note** under the logo card for a GIF logo: "Animated GIF: it animates on the stream." / "... It is long, so N of its M frames are used (same speed)." / "This GIF cannot animate on the stream (reason). The stream shows its first frame." (amber). Replaces "the broadcast uses its first frame". The GIF is fetched once to read its frame delays (`BrandRepository.gifLogoPlan`, cached).
* **Tests**: `GifFramesTest` (delays, parsing, frame selection and delay merging, caps, the plan for a logo, wall-clock frame index, a real LZW encoder round trip incl. code-width growth and table resets, interlace, transparency, disposal).
* **Not verifiable without a device**: bitmap creation and scaling of up to 150 frames (heap use near the 96 MB cap on low-memory phones), GL upload cost per frame change, how the logo looks while scaling into the window.

  1. **A single failed list load hid the whole feature until the app was restarted.** `PresetController.refresh()` set `available = false` for ANY failure when nothing was loaded yet (offline at start-up, a 5xx, a timeout while ~15 start-up requests queue, a captive page). The Customize sheet only shows "Save as preset" `if (ps.available)` and Home only shows "+ New preset" `if (ps.available)`, so both silently vanished. Now ONLY 404 / 405 / 501 (endpoint missing = older server) hides the section; anything else keeps it, sets `loadError` ("Could not load your presets. ...", amber, with "Try loading presets again" on Home and a silent retry whenever Home or the Customize sheet opens) and Save still works.
  2. **Server validation errors were swallowed as "Request failed (400)".** The real server wraps Nest's response (`{statusCode, message: {message: [...], error, statusCode}, timestamp}`), so a 400 carries an ARRAY one level down, and `ApiClient.errorMessage` only read strings there. It now reads strings and arrays at any depth (all features benefit). Presets show "Could not save the preset: <server words>" (for example the 20-preset limit "You can keep up to 20 presets. Delete one to save another.", 422 "One or more destinationIds do not belong to this account"). The old tests invented a flat error body, which is why this was never caught: `ServerErrorShapeTest` now uses bodies captured from the real server.
  3. **No feedback and no explanation.** The name field started empty and Save was simply greyed out; after a save the only change was a button label. Now the field starts with a proposal (the ticked channels, "YouTube + Facebook", unique among saved names: `suggestPresetName`), a blank name says "Give the preset a name to save it.", the button shows "Saving...", and success shows a green "Preset saved" / "Preset updated" in the sheet and on Home (4 s).
  4. **Stale list.** After a save/update/delete the controller now re-reads `GET /presets` (so presets made on the website or another phone show up and the order is the server's), and Home pulls the list again every time it opens. A 404 on update/delete (deleted elsewhere) drops the card and says "That preset no longer exists ..." instead of leaving a dead card; deleting something already deleted counts as done; an unexpected exception can no longer crash the view model (it becomes a message).
* **Diagnostics**: every preset call writes a line to the event log (`Diag`, part of "Share crash report", and logcat tag `StreamBirdPresets`): `presets: list ok, 3 preset(s)`, `presets: create failed HTTP 400 <message> body=<first 200 chars>`, `presets: save tapped, 2 destination(s), quality hd, shape portrait, kit true`. `ApiException` now carries the first 300 characters of the raw body (`body`, never shown to the user).
* **Still true / not changed**: the implicit "Quick start" card for servers without presets; a preset stores orientation, channels, kit, quality, ticker (not the title, which comes from the kit default, 22c). `brandKitId` is omitted for "automatic" (server: omitted = the destination's / account default kit; `null` would mean "no kit").
* **Tests**: `PresetsServerReplayTest` (a MockWebServer that re-implements the server's routes, validation messages, 20-preset limit, ownership checks and error envelope; save/update/use/delete/restart, 400/409/422 words, a failed first load keeps the section, only a missing endpoint hides it, HTML page, expired session, presets made elsewhere, deleted elsewhere), `PresetControllerTest` (new expectations for load failures, 404/405/501, notices, re-read, logs, unexpected exceptions), `ServerErrorShapeTest`, `PresetLogicTest.suggestPresetName`, `LiveServerPresetsTest` (manual, real server).
* **Not verified on a device**: the Compose layout of the sheet, the keyboard with the name field, the 4 s notice on Home, and whether the founder's phone hit defect 1 (it cannot be told from here; the new log lines will say if a list load fails).

### 22b. Brand images up to 8 MB (server cap raised from 4 MB; thumbnail stays 2 MB)
* **Limits** (`brand/ImageHeader.kt`, `BrandSizes.kt`): `MAX_ASSET_BYTES` / `BrandFileLimits.MAX_BYTES` = 8 MB for logo, wallpaper, ads (landscape, portrait, L-shaped frame); `ThumbnailLimits.MAX_BYTES` = 2 MB (unchanged); side 8192 px unchanged. 8 MB exactly is accepted, one byte more is refused ("The image is too large -- the limit is 8 MB per file."). Texts updated: slot help lines ("... up to 8 MB."), Brand screen ("PNG, JPG or WebP (GIF for logos and ads), up to 8 MB and 8192 px."). Phone-only per-stream ads (never uploaded) keep the website's 12 MB cap.
* **Upload path streams the file** (`brand/UploadPrep.kt`, `data/StreamingBody.kt`, `BrandRepository.uploadPicked`): before, the picked image was read into a `ByteArrayOutputStream`, copied to an array, then wrapped in the multipart body (3-4 copies; 8 MB would have been about 30 MB of heap). Now: the size comes from the provider (asset descriptor / `OpenableColumns.SIZE`; unknown = counted by reading through once, keeping nothing); an oversize file is refused from its size alone without being opened; only the first 512 KB are read to find format and pixel size (a JPEG with more metadata than that is re-read once); the body is `StreamingFileBody`, which copies from the Uri to the socket in small reads with the exact `Content-Length` (not chunked). A file that changes length while uploading fails with a message instead of sending garbage.
* **Timeouts for slow uplinks** (`ApiClient.uploadHttp`): same cookie jar, Origin interceptor and connection pool as the normal client, but write timeout 60 s (OkHttp counts a write that makes no progress, not the whole call; the default 10 s fails on a weak mobile link), read timeout 120 s (the server validates and stores the file in object storage before it answers) and no overall call timeout (a slow but moving 8 MB upload may take minutes; the coroutine can still be cancelled). Used by `uploadAsset`, `uploadAssetStreaming` and the stream thumbnail PUT. Normal API calls keep 15 s connect / 30 s read and now 30 s write.
* **Decoding** was already bounded and stays: logo `decodeLogo` (inSampleSize until the long side is about 1024, then capped at 2048), kit ads `stillSampleSize` for the area they cover, frame window detection (long side <= 1280), Coil sizes previews to their views, animated GIF caps from 1.0.8 (150 frames, 96 MB) unchanged. `assetFile` downloads up to 10 MB (more than the 8 MB cap) for the broadcast.
* **Tests**: `UploadPrepTest` (8 MB ok / +1 byte refused for logo, wallpaper, ad; 4 and 6 MB now accepted; thumbnail 2 MB ok / +1 refused; oversize refused without opening; only the head is read; unknown size counted; big-metadata JPEG; GIF as wallpaper; cannot open), `StreamingUploadTest` (8 MB through MockWebServer intact, with Content-Length, read in small steps; short/long file fails; re-writable; upload client timeouts and shared interceptors/cookie jar; server refusal text), `ImageHeaderTest`, `BrandSizesTest`, `KitThumbnailTest`.
* **Not verified**: a real 8 MB upload over a real phone uplink and against the server with its raised cap (the other agent's PR); memory use of GL decode for an 8192 px logo on low-RAM phones.

### 22c. Brand kit default title and description
* **Contract** (server, implemented separately; field names fixed): `GET/POST/PATCH /brand-kits` carry `title` (max 100) and `description` (max 5000 = the stream description limit, `CreateStreamDto`), `string | null`, trimmed; PATCH: omitted = unchanged, `null` or blank = cleared. They are DEFAULTS for streams that use the kit: the stream's own non-blank value wins, a blank/omitted one falls back to the resolved kit's on the server; the stream answer may say which came from the kit (`titleFromKit` / `descriptionFromKit`, read leniently as any JSON, only logged).
* **Kit editor**: "Default title" (counter n/100) and "Default description" (counter n/5000, 3-8 lines) under the name, hint "Used for new streams that don't have their own title or description. You can change it on each stream." Saved with the kit: PATCH sends each field ONLY when it changed (trimmed, capped; blank clears with an explicit null), POST only when filled, so an older server never sees them; an older server's "property title should not exist" becomes a plain sentence (`KitCompat.NO_KIT_TEXT`). A kit from an older server (fields absent) parses with nulls.
* **Setup / Customize title** (`brand/KitText.kt`, `StudioViewModel.watchKitTitle`): while the host has not typed, the Title field follows the default title of the kit in use (the chosen kit, or the automatic one for the ticked channels; only while the brand kit is in use, like the thumbnail note), updates when the kit selection, the ticked channels or the loaded kits change, and a note reads "From brand kit <name>" (Setup under the field, camera screen under the big title). A typed title always wins and is never overwritten (an emptied field counts as typed; then "Left blank: the title of brand kit <name> is used."). Opening the title dialog and pressing Done without a change is not typing. At Go live a blank title becomes the kit's default title (`KitText.finalTitle`), else "Mobile stream" as before; the Go-live-now preset flow works the same because presets do not store a title.
* **Description**: the app has no description field and does not send `description` to `POST /streams`, so it relies on the server fallback and only shows "Description: from brand kit <name>" under the title when the kit in use has one.
* **Tests**: `KitTextTest` (limits, trimming/caps, untouched vs typed, kit switched, kit without default, blank, dialog without change, final title, PATCH/POST bodies with only known fields, set/clear/unchanged, JSON tolerance of older servers and odd `...FromKit` values, compat sentence).
* **Not verified**: the server side (not deployed when this was written), the Compose wiring of the live title prefill (a `combine` of the brand state, kit choice and setup in `StudioViewModel`, not unit-tested because the view model needs Android/Hilt), the layout of the new editor fields.
